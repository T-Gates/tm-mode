# 팀모드 운영 지침

이 세션은 팀모드다. 팀의 메모리(맥락)를 적극 활용해 일한다.

## 작업 전 — 맥락을 먼저 찾는다
- 어떤 작업을 시작하기 전, 관련 맥락을 조회한다 — 팀 메모리(`tm-memory`) + 세션로그(이전에 누가 무엇을·왜 했는지).
- 팀이 쌓아둔 제품·결정·규칙·작업 이력을 모르고 진행하지 않는다.

## 메모리가 비어 있으면 — 채우게 요구한다
- 팀 메모리에 맥락이 부족하면, 사용자에게 채워달라고 요구한다:
  > "이 작업을 제대로 하려면 팀 맥락이 필요해요 — X를 메모리에 넣어주실 수 있나요?"
- 빈약한 맥락으로 추측해 진행하지 않는다.
- **기존 문서가 있으면 memory로 옮길 것을 적극적으로 권한다** — 노션·구글독스·컨플루언스 등에 이미 써둔 게 있으면 그걸 가져오는 게 제일 빠르다. "혹시 이미 정리된 문서 있으세요? 있으면 바로 옮겨드릴게요"라고 먼저 물어본다.
- **`product/tech/`가 비어있으면**: GitHub 레포 링크를 요청하고, 받으면 백그라운드 서브에이전트로 레포를 분석해 `stack.md`·`features.md`를 자동으로 채운다.

## 핵심 맥락 (팀이 갖춰야 할 것)
- **제품·브랜드**: 무엇을 만드나, 핵심 기능, 핵심 고객, 브랜드 철학(차별화·가치관), 로드맵
- **그라운드룰**: 팀이 일하는 방식, 코드 컨벤션, 지켜야 할 원칙
- **결정사항**: 왜 그렇게 정했나 (반복 논의 방지)
- **아키텍처·기술 스택**: 시스템 구조, 핵심 기술(DB·프레임·언어), 제약 사항

## 메모리는 동사로 쓰는 쪽이 낫다
- 조회 `tm-memory` / 추가·수정 `tm-manage-memory`.
- `memory/`를 직접 Edit/Write 해도 막히지는 않는다. INDEX·frontmatter·백링크는
  직접 챙겨야 한다. 네이티브 편집 훅이 실행되면 해당 파일의 자동 커밋·push를 시도한다.
- 마지막 Git 작업의 실패가 남아 있으면 로그 작성 여부와 별개로 5프롬프트마다
  공유 미확인을 알린다. 이 알림 훅 자체는 Git 작업을 실행하지 않는다.
- 셸/Python으로 직접 쓴 파일은 네이티브 편집 훅을 거치지 않는다. 쓰기 후
  `python3 "<team-root>/infra/teammode.py" commit --root "<team-root>" --message 'docs: update team memory' --paths 'memory/team/decisions.md memory/team/INDEX.md' --push`
  를 명시적으로 실행한다. `--paths`에는 실제로 수정한, 알고 있는 레포 상대 파일 경로만
  공백으로 구분해 넣는다. 와일드카드나 `memory/` 전체를 지정해 무관한 변경까지
  포함하지 않는다. 경로 자체에 공백이 있으면 이 CLI 형식으로 표현할 수 없다.
  `--paths`를 빼거나 비워 전체 변경을 커밋하지 않는다.
- SessionStart 동기화 실패나 5회 공유 실패 알림을 받으면, 다음 작업으로 본인 세션로그의
  실제 미커밋 경로를 확인해 위 `commit --paths … --push`를 1회 실행한다. 이미 커밋됐다면
  같은 엔진의 `pull --root "<team-root>"`로 동기화(fetch/rebase/push)를 1회 재시도한다.
  다른 멤버·코드·사용자가 별도로 stage한 변경을 임의로 포함하지 않는다. 계속 실패하면
  원인을 남기고 다음 기회로 넘기며, 같은 이벤트 안에서 반복하지 않는다.
- 사용자가 팀에 남길 결정·메모리를 말하면 `tm-manage-memory`로 쌓는다. 쌓인 메모리는 다음 세션에 자동 주입된다.

## 엔진 업데이트 알림이 보이면 — 먼저 물어본다
- 세션 시작 맥락에 엔진 업데이트 알림(`tm-mode update`로 적용하라는 문구)이 보이면, 세션 시작에 바로 사용자에게 알리고 적용할지 제안한다: "tm-mode 엔진 업데이트가 있어요 — `tm-mode update`로 적용할까요?"

## teammode 자체에 문제가 보이면 — 본레포에 제보를 제안한다
- tm-mode 제품(`infra/`)의 버그·불편·개선점을 발견하면 묻어두지 말고, 사용자에게 제보를 제안한다:
  > "이거 teammode 본레포에 제보할까요?"
- 제보는 `tm-contribute` 스킬로 — 먼저 **본레포 대조 진단**으로 "진짜 본레포 버그인지, 우리 인스턴스의 로컬 문제인지"를 가린다(헛이슈 방지). 인스턴스 문제면 `tm on`(sync)을 권하고, 본레포 버그면 GitHub 이슈로 올린다.
- 우리가 겪은 문제는 다른 팀에게도 도움이 된다 — 제품이 같이 자란다.
